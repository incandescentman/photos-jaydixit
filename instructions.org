* 🎯 Overview

This guide walks you through uploading photos to Cloudinary with proper metadata (captions, titles, tags) and generating Astro content files for your website.

* Canonical Photo Ingest And Publication Protocol

The publication workflow has two separate jobs: establish truthful portable metadata, then wire each photograph into the intended site surface. A Cloudinary upload by itself does not make a photograph visible on this site.

** Agent-fronted private batch workflow

The private publisher turns a Lightroom export into a reviewable, resumable manifest. Planning is read-only:

#+begin_src bash
cd /Users/jay/Dropbox/github/photos-jaydixit
pnpm photo:publish plan /path/to/lightroom-export \
  --gallery red-carpet/tiff-2025 \
  --output /path/to/publication-plan.json \
  --commons-category "Approved existing Commons category" \
  --commons-gallery "https://commons.gallery/@account/album"
#+end_src

Repeat ~--commons-category~ and ~--commons-gallery~ for multiple values. A planned photograph defaults to the local portfolio, Wikimedia Commons, and Cloudinary; any destination can be disabled in the reviewed manifest. Planning never copies or uploads a file.

For a minor correction to the same photograph already on Commons, plan an explicit new-version replacement. Use the existing Commons filename exactly; this preserves the file page, categories, history, and every Wikimedia use of that filename.

#+begin_src sh
pnpm photo:publish plan /path/to/corrected-photo.jpg \
  --gallery red-carpet \
  --output /path/to/replacement-plan.json \
  --no-portfolio \
  --cloudinary none \
  --commons-mode new-version \
  --commons-existing-filename "Existing_Commons_filename.jpg" \
  --commons-replacement-comment "Minor color correction from the photographer's original RAW file."

pnpm photo:publish preview /path/to/replacement-plan.json
#+end_src

The read-only preview verifies the source checksum, local dimensions, exact live Commons target, current revision checksum and dimensions, and proposed replacement comment. New-version execution refuses a missing target, does not rewrite the Commons description page, and verifies that the live file checksum changed after upload.

The batch gallery is only a planning default. For a mixed export, the agent changes ~destinations.portfolio.gallery~ per photograph after the event is established. Execution rebuilds the local destination path and, by default, the Cloudinary public ID from that reviewed per-photo gallery instead of trusting a stale generated path.

The manifest keeps ~metadata.capture_date~ from EXIF separate from the approved event-local ~metadata.event_date~ used on Commons and in publication metadata. When they differ, the preview shows both and execution requires ~review.event_date_approved: true~. Never silently treat the camera calendar date as the event-local date across midnight or time-zone differences.

For each photograph, the agent asks only for missing facts and judgments. The three independent review dimensions are:

- Quality :: ~unreviewed~, ~reject~, ~fine~, or ~great~
- Favorite :: ~true~ or ~false~; a favorite must also be ~great~
- Publication destinations :: local portfolio, Wikimedia Commons, Cloudinary, homepage highlight, and any Commons Gallery albums

Catalog presence, valid metadata, technical sharpness, celebrity, and agent preference do not establish quality or favorite status. Only Jay assigns those judgments after visual review. Confirmed names go in the embedded people field; an unknown person remains a descriptive unresolved identity in the manifest. Favorite status does not imply homepage publication: ~destinations.homepage.enabled~ is a separate explicit decision and is valid only for a ~great~ favorite.

After Jay has approved the complete preview, the agent records ~approved_at~, marks each reviewed photograph ~approved~, and runs:

#+begin_src bash
pnpm photo:publish execute /path/to/publication-plan.json --confirm PUBLISH
#+end_src

Execution begins with a read-only gate that rechecks source hashes, existing Commons categories, ignored owner-only Pywikibot credential storage, noninteractive Wikimedia login, and Cloudinary authentication before any portfolio copy or upload. It never overwrites a different local asset or Cloudinary public ID. It persists and prints the phases ~preflight~, ~portfolio~, ~commons~, ~cloudinary~, ~homepage~, ~commons-gallery~, ~inventory-commons~, and ~inventory-site~, saving destination receipts and phase status so an interrupted batch can be diagnosed and resumed from the manifest alone. An explicitly enabled homepage destination creates or verifies the local highlight, its ~highlights/~ Cloudinary asset, homepage configuration entry, exact image dimensions, and receipt. Execution keeps portfolio changes local and never commits, pushes, or deploys.

Pywikibot authentication uses the ignored owner-only ~.passwd~ file referenced by ignored ~user-config.py~; account-specific ~pywikibot-*.lwp~ cookies are ignored too. Do not duplicate the BotPassword in ~.env~. Credential diagnostics may report only presence, ignore status, permissions, format, length, or a sanitized HTTP status; never print a secret-bearing line, clipboard value, complete SDK error object, or request options. Cloudinary Admin API error objects can contain the Basic-auth credential under ~request_options.auth~, so catch and replace them with a sanitized error before any console output.

The canonical cross-destination record is [[file+emacs:/Users/jay/Dropbox/roam/photography/20260902015339-photo_publication_inventory.org][📄 Photo Publication Inventory]]. For “Have I uploaded this person or photograph before?” or “Is this photograph on my site?”, search that file first. It keeps the portfolio repository source, verified-live ~photos.jaydixit.com~ state, Cloudinary configuration, and Wikimedia Commons upload history distinct. Run ~pnpm photo:inventory freshness~; only run ~pnpm photo:inventory sync~ when the registry is missing or stale. The publication executor refreshes it automatically after a completed publication batch.

[[file+emacs:/Users/jay/Library/CloudStorage/Dropbox/github/photos-jaydixit/src/pages/photo-inventory.json.ts][📄 photo-inventory.json endpoint]] generates the deployed site manifest at ~https://photos.jaydixit.com/photo-inventory.json~. Until the endpoint reaches production through an explicitly authorized push and deployment, the inventory retains a one-time route-verified production snapshot; source presence must not be described as live deployment.

A Commons Gallery album does not host the media itself. The agent first uploads the reviewed file to Wikimedia Commons, then uses the authenticated album editor’s ~Manage Media~ → ~Add by Filename~ flow to add the resulting Commons filename, reorder it, and set the album caption. That browser change requires Jay’s action-time approval just like the uploads.

** 1. Preflight The Lightroom Export With Exwalker

When Jay supplies filenames for new photographs without a directory, check [[file+emacs:/Users/jay/Downloads][📁 /Users/jay/Downloads]] first before searching elsewhere or asking for the path.

Use [[file+emacs:/Users/jay/Dropbox/github/exwalker][📁 /Users/jay/Dropbox/github/exwalker/]] before copying or uploading new exports:

#+begin_src bash
cd /Users/jay/Dropbox/github/exwalker
./exwalker preflight /path/to/lightroom-export
./exwalker preflight /path/to/lightroom-export \
  --check \
  --required title,caption,keywords,people,event
#+end_src

The guided pass is the factual gate: Jay identifies the people and supplies or approves the title, caption, event, and keywords for every photograph. Exwalker embeds those fields in exported JPEG/TIFF files, creates a one-time hidden backup before the first write, rereads every write, and records resumable progress in ~.exwalker-session.json~.

Do not treat ~npm run photo:validate~ as proof that a caption or identity is true. The portfolio validator checks whether merged fields are present and can fill a missing title from a caption or a missing caption from a title. Exwalker’s human-reviewed audit establishes factual readiness; ~photo:validate~ is the downstream compatibility check.

** 2. Give Published Copies Semantic Filenames

Filenames, folder paths, ~tags.json~, and [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/data/people.json][📄 /Users/jay/Dropbox/github/photos-jaydixit/src/data/people.json]] drive the public presentation.

*** First, check your metadata is complete:
#+begin_src bash
npm run photo:validate -- ./src/gallery/photos
#+end_src

This validates the merged metadata for each photo:
- embedded EXIF/IPTC/XMP metadata already on the file
- folder defaults from ~tags.json~
- per-file overrides from ~tags.json~

*** Preview what will happen (dry run):
#+begin_src bash
node scripts/photo-cli.js upload ./src/gallery/photos --dry-run --verbose
#+end_src

*** If validation passes, upload for real:
#+begin_src bash
npm run photo:upload -- ./src/gallery/photos
#+end_src

Use this workflow only when intentionally publishing a Cloudinary-backed album or another Cloudinary consumer. Filesystem gallery publication does not require it. The main CLI will:
- merge metadata from the file and ~tags.json~
- validate the merged metadata
- write the merged caption/title metadata back into the source image file
- upload the image and sync the same metadata to Cloudinary
- generate Astro album content

*** Force upload even with validation errors:
#+begin_src bash
node scripts/photo-cli.js upload ./src/gallery/photos --force
#+end_src

Behavior notes:
- The full CLI uses ~overwrite: true~. Uploading the same ~public_id~ overwrites the existing asset.
- The full CLI writes merged metadata back into the original file before upload unless you use ~--dry-run~ or ~--no-embed-metadata~.
- The basic uploader and EXIF uploader skip existing assets unless you remove them or change filenames.

* 🆘 Troubleshooting

** "Missing required field: caption/title"

You need to add metadata to your photos. Either:
1. Use ExifTool to add IPTC:Caption-Abstract and XMP-dc:Title
2. Add captions in tags.json
3. Use --force flag to upload anyway (not recommended)

** "ExifTool is not installed"

Install it:
#+begin_src bash
brew install exiftool
#+end_src

The script now checks for duplicates. To re-upload:
1. Delete from Cloudinary Media Library first
2. Or use a different filename

** Can't find uploaded photos

Check the Cloudinary console:
- URL: https://console.cloudinary.com/console/dszpm7yps/media_library
- Look in the "photos" folder

* 📐 Content Collection Schema Notes

- Albums live under ~src/content/albums/~ as JSON. Filename is ~<album.slug>.json~.
- The current schema (in ~src/content/config.ts~) expects keys:
  - top-level: ~title~, ~date?~, ~coverPublicId?~, ~tags?~, ~photos: [{ publicId, alt, width?, height? }]~
  - Extra fields written by the CLI (e.g., ~photoCount~, ~uploadedAt~, ~lastModified~, per-photo ~caption~/~tags~/~city~) may be ignored by schema consumers; the Gallery uses ~publicId~, ~alt~, ~width~, ~height~.
- If an album page 404s, ensure a JSON file exists for that slug and it validates against the schema.

* 🔐 Environment & Behavior Notes

- Full CLI uses ~overwrite: true~ (re-uploads replace a matching ~public_id~).
- Basic and EXIF uploaders skip existing assets (to force, delete in Cloudinary or change filename/public_id).
- Keep filenames lowercase with hyphens; use underscores to separate parts: ~subject_event_year.jpg~.
- ~album.slug~ should be unique and hyphenated; it determines the JSON filename and route under ~/albums/<slug>~.
