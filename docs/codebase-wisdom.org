#+TITLE: Codebase Wisdom
#+DATE: 2025-10-03

* 2026-07-06 - Local PhotoSwipe Failures Can Be Vite Optimized-Dependency Cache Drift

** Trigger
The homepage lightbox opened correctly on [[https://photos.jaydixit.com/][photos.jaydixit.com]] but clicking the same kind of photo on [[http://localhost:4327/][localhost]] did nothing.

** Mechanism
The local dev page had the correct ~portfolio-lightbox~ anchors and PhotoSwipe data attributes, but the browser console showed Vite returning ~504 (Outdated Optimize Dep)~ for ~node_modules/.vite/deps/photoswipe.js~. In that state, the PhotoSwipe dynamic import never resolves, so clicks look like a broken lightbox even though the production bundle is fine.

** Fix
Check the browser console before changing lightbox code. If the error is Vite's outdated optimized dependency for ~photoswipe.js~, force local dependency reoptimization, usually by restarting the dev server or clearing Vite's generated dependency cache. Verify production or a fresh build before treating it as an application regression.

** Rule of Thumb
If PhotoSwipe works in production but not in local dev, first distinguish code failures from Vite dependency-cache failures. A ~504 (Outdated Optimize Dep)~ on ~photoswipe.js~ is a local dev-server artifact, not proof that the shipped lightbox is broken.

* 2026-06-24 - ESLint Flat Config Must Ignore Playwright Artifact Directories Directly

** Trigger
After adding Playwright, a parallel verify run had ~pnpm lint~ fail with an =ENOENT= while ESLint was scanning ~test-results~ as Playwright was creating and cleaning generated artifacts.

** Mechanism
Repo-level =.gitignore= keeps Playwright artifacts out of commits, but the ESLint flat config has its own explicit ignore list. If generated artifact directories are not listed there, ESLint can still walk them during broad commands like ~eslint . --ext .ts,.js,.astro~.

** Fix
Add ~playwright-report/**~ and ~test-results/**~ to the top-level ~ignores~ block in ~eslint.config.js~.

** Rule of Thumb
When adding a generator-backed test tool, update both =.gitignore= and tool-specific ignore lists. Generated directories should not be lint or typecheck inputs.

* 2026-06-24 - PhotoSwipe Keyboard Tests Need To Wait For The Open Transition To Settle

** Trigger
The new Playwright e2e test could click a homepage or gallery photo and see ~PhotoSwipe~ visibly open, but an immediate synthetic ~Escape~ keypress did not close the lightbox in bundled Chromium. The same interaction worked in a slower manual-style browser probe.

** Mechanism
~PhotoSwipe~ can be visible and carrying ~=pswp--open=~ before it is fully settled for keyboard interaction. Playwright is fast enough to send ~Escape~ during that opening window, so the key event can be ignored even though the UI looks open in the failure screenshot.

** Fix
For keyboard-close tests, wait for the root lightbox to be visible, wait for the ~=pswp--open=~ class, then allow a short settle interval before pressing ~Escape~.

** Rule of Thumb
When testing animated overlays, assert the stable open state before keyboard shortcuts. If a screenshot shows the overlay open but the shortcut failed, check timing before assuming the app option is missing.

* 2026-04-27 - Cropped PhotoSwipe Thumbnails Need Explicit Metadata, And Capped Lightbox Images Must Advertise Their Real Max Size

** Trigger
The repo still had a mix of cover-cropped thumbnails, uncapped full-resolution lightbox targets, and lightbox dimensions that described the original image even when the served lightbox source was intentionally capped.

** Mechanism
Two separate PhotoSwipe assumptions were easy to violate:

- If the visible thumbnail uses ~=object-fit: cover=~, PhotoSwipe assumes the preview is *not* cropped unless you set ~=data-cropped="true"=. The open/close animation can feel subtly wrong otherwise.
- If you cap the lightbox source (for example to ~=2200px=~ or ~=2800px=~) or supply ~=data-pswp-srcset=~, then ~=data-pswp-width=~ / ~=data-pswp-height=~ should describe the *largest delivered lightbox image*, not the original full-resolution source.

Using the original dimensions with a capped lightbox still preserves aspect ratio, but it overstates available zoom detail and makes the responsive source metadata less truthful than it should be.

** Fix
- Add ~=data-cropped="true"= anywhere the clickable preview is visibly cropped:
  - ~src/pages/index.astro~
  - ~src/pages/gallery/[...folder].astro~
  - ~src/components/PhotoGrid.astro~
  - ~src/pages/before-after.astro~
- When lightbox sources are capped or responsive, set ~=data-pswp-width=~, ~=data-pswp-height=~, and ~=data-pswp-srcset=~ to match the largest delivered lightbox variant.

** Rule of Thumb
If a PhotoSwipe transition feels "off" from a cover thumbnail, or zoom seems to promise more detail than the slide actually has, check two things first:
- missing ~=data-cropped="true"=
- dimensions that describe the original file instead of the capped lightbox source

* 2026-04-27 - Astro Asset ~=.src= Can Break PhotoSwipe And GLightbox In Dev

** Trigger
Lightbox links built from imported Astro image metadata looked reasonable in source, but opened broken images in development even while the thumbnails themselves still rendered.

** Mechanism
For imported Astro assets, ~=ImageMetadata.src=~ can resolve to a raw =/@fs/...= path in dev. The visible ~<Image>~ often still works because the browser prefers a valid optimized image from ~=srcset=~ or another transformed URL, so the page thumbnail looks healthy.

The trap is that PhotoSwipe or GLightbox opens the anchor ~=href=~, not the browser's chosen ~=currentSrc=~. If the anchor still points at the raw =/@fs/...= path, the lightbox fetch can fail even though the inline image looks fine.

This repo had the risky pattern in:
- ~src/pages/before-after.astro~
- ~src/components/PhotoGrid.astro~

** Fix
Generate a served image URL for the lightbox target instead of reusing raw metadata ~=.src=~.

- For Astro-authored asset components, build the lightbox href with ~=getImage()=~
- For DOM-enhanced content images, prefer ~=img.currentSrc || img.src=~ once the image is actually rendered

** Rule of Thumb
If a lightbox image fails in Astro dev but the thumbnail still renders, inspect the anchor ~=href=~ first. If it starts with =/@fs/=, the lightbox target is wrong even if the on-page image looks correct.

* 2026-04-01 - Legacy ~=gallery= Cloudinary Transforms Can Break Otherwise Valid Images

** Trigger
Blog images on ~/blog/nobel-portrait-session/~ were broken even though the underlying Cloudinary public IDs were correct and directly fetchable.

** Mechanism
The shared helper in ~src/lib/cloudinary.ts~ was still honoring ~=PUBLIC_CLOUDINARY_TRANSFORM=gallery~ and generating URLs like ~.../image/upload/t_gallery,w_1600/...~.

That named transform no longer exists on Cloudinary, so requests fail with ~=Unknown transformation gallery=~. This is easy to miss because the public ID itself is valid, and swapping only the transformation string to ~f_auto,q_auto,w_1600~ immediately makes the same asset load.

The bug is worse than a single broken page because blog hero images, related-post cards, and any helper-generated Cloudinary URL all inherit the same transform logic.

** Fix
Treat the legacy ~=gallery=~ value as invalid and fall back to explicit transforms instead of blindly emitting ~t_gallery~.

- In ~src/lib/cloudinary.ts~, default to ~f_auto,q_auto~ when ~=PUBLIC_CLOUDINARY_TRANSFORM=~ is missing or still set to ~=gallery=~
- In MDX posts that hardcode old Cloudinary URLs, replace ~t_gallery,...~ with explicit transforms such as ~f_auto,q_auto,w_1600~
- Verify suspicious Cloudinary failures with ~curl -I~; if the same public ID loads under ~f_auto,q_auto~ but not ~t_gallery~, the transform is the problem, not the asset

** Rule of Thumb
Treat named Cloudinary transforms as external configuration that can drift or disappear. If a page breaks but the public ID is valid, test the same asset with explicit ~f_auto,q_auto~ transforms before assuming the image is missing.

* 2026-04-01 - Blog Post Images Need Template-Level PhotoSwipe Wiring

** Trigger
Images on ~/blog/nobel-portrait-session/~ rendered correctly but clicking them did nothing, even after the broken image URLs themselves were fixed.

** Mechanism
Blog post body content is rendered from Markdown/MDX as plain ~<img>~ tags inside ~src/pages/blog/[slug].astro~. Unlike gallery pages or ~/before-after/~, those images are not authored with PhotoSwipe wrappers, dimensions, or captions.

That means there is nothing for PhotoSwipe to attach to unless the blog template itself enhances the rendered images. Fixing one post by hand would just move the bug around to the next essay.

** Fix
Handle blog-image lightbox behavior in the shared blog post template, not in individual posts.

- Give the article a stable gallery container
- Wrap rendered blog-body and hero images in ~=portfolio-lightbox=~ anchors at runtime if they are not already linked
- Populate ~=data-pswp-width=~, ~=data-pswp-height=~, and ~=data-pswp-caption=~ from the image element
- Initialize PhotoSwipe from a hoisted script so Astro bundles the code into ~/_astro/*.js~

** Rule of Thumb
If content comes from Markdown/MDX, assume it will emit plain HTML. Cross-cutting behavior like PhotoSwipe belongs in the page template or renderer pipeline, not in individual content files.

* 2026-03-31 - Homepage Cloudinary IDs Can Drift From Local Highlight Filenames

** Trigger
Local highlight files were renamed to cleaner subject-based names such as ~jude-law_tiff.jpg~ and ~ron-livingston_sxsw-office-space-event_2024.jpg~, but the landing page started serving broken Cloudinary URLs.

** Mechanism
The homepage derives Cloudinary public IDs from ~=filename=~ in ~src/data/homepage-images.js~. That works only if the remote Cloudinary asset was uploaded under the same basename.

Once a local file is renamed without also renaming or re-uploading the Cloudinary asset, the landing page starts requesting a public ID that does not exist, even though the local file and metadata are correct.

** Fix
Allow homepage entries to carry an explicit ~=cloudinaryPublicId=~ override and fall back to the filename-derived ID only when local and remote names still match.

- Keep canonical local filenames meaningful in ~/src/gallery/highlights/~
- In ~/src/data/homepage-images.js~, set ~=cloudinaryPublicId=~ when the Cloudinary asset still lives under an older name
- In ~/src/pages/index.astro~, prefer ~=cloudinaryPublicId=~ over the derived ~=highlights/{basename}=~ pattern

** Rule of Thumb
Treat Cloudinary public IDs as external identifiers, not as guaranteed mirrors of local filenames. If a local rename happens after upload, either rename the Cloudinary asset too or add an explicit override in homepage data.

* 2026-03-31 - Sibling Source WebP Files Must Be Excluded From Gallery-Style Source Lists

** Trigger
Routes like ~/gallery/events/nobel/~ and the gallery index surfaced duplicate photos because both ~.jpg~ and sibling source ~.webp~ files were being treated as separate source images.

** Mechanism
Under ~/src/gallery/photos/~, source ~.webp~ files are derivative siblings of canonical source images, not distinct photos. Routes that count or list raw files by folder, such as ~src/pages/gallery/index.astro~, ~src/pages/gallery/[...folder].astro~, and ~src/pages/upload-to-commons.astro~, will overcount and duplicate cards if they glob ~=webp=~ alongside ~jpg/jpeg/png/gif~.

Routes that dedupe by slug can safely continue to glob ~.webp~, but gallery-style source-list pages should not.

** Fix
Exclude ~.webp~ from raw gallery photo globs on routes that build folder counts, source-photo lists, or upload queues.

- Use patterns like ~**/*.{jpg,jpeg,png,gif}~ for folder galleries, gallery indexes, and Commons upload helpers
- Keep ~.webp~ only on routes that intentionally dedupe by slug and source priority

** Rule of Thumb
If a route is treating files as source photos rather than as renderable asset variants, do not glob sibling ~.webp~ files.

* 2026-03-31 - Portrait Pages Need Explicit Photo Mappings For Group Shots And Legacy Filenames

** Trigger
Portrait pages initially worked only when the filename started with the subject slug, which left highlight-only people, group portraits, and event-style filenames invisible or stuck on ~/404~ pages.

** Mechanism
The original portraits matcher only looked at the subject slug, defined as the part of the filename before the first ~=_=. That works for files like ~dave-franco_sundance_2025.jpg~, but it fails for cases like:

- ~group-portrait_ana-de-armas-sydney-sweeney-ron-howard_2024.jpg~
- ~2024-03-09_SXSW_Conan_Nick-Kroll_Office-Space_events_07141.jpg~
- legacy highlight filenames that do not begin with the person slug

Highlight-only pages also need the underlying image files to exist locally in ~/src/gallery/highlights/~. Metadata entries in ~src/data/homepage-images.js~ and ~src/data/image-metadata.json~ are not enough by themselves.

** Fix
Keep the simple ~=match= prefix logic for normal filenames, but add explicit ~=photoSlugs= overrides in ~/src/data/people.json~ for exceptions.

- Portrait routes should scan both ~/src/gallery/photos/~ and ~/src/gallery/highlights/~
- Exact ~=photoSlugs= matches should be checked before prefix-based subject matching
- Person-page captions should reuse homepage captions from ~/src/data/homepage-images.js~ when available, especially for group shots and event-style filenames
- If a portrait page is backed only by highlights, render the card without forcing a broken gallery detail link

** Rule of Thumb
If a person is visible on the site but their filename does not cleanly start with their slug, do not invent more filename parsing. Add an explicit ~=photoSlugs= mapping and make sure the corresponding file exists locally.

* 2026-02-18 - PhotoSwipe Can Distort If It Uses Cropped Thumbnail Dimensions

** Trigger
On gallery folder pages (example: ~/gallery/events/nobel~), images opened in PhotoSwipe looked squeezed/distorted even though thumbnails looked fine.

** Mechanism
Masonry thumbnails are rendered with heuristic crop sizes (~320x480~, ~648x480~, etc.) for layout, but PhotoSwipe was using those thumbnail dimensions to calculate slide ratio while loading the full image.

If PhotoSwipe receives the crop dimensions instead of the full source dimensions, slide geometry is wrong and images appear stretched.

** Fix
Always pass true source dimensions to PhotoSwipe, not masonry crop dimensions:

- Add ~data-pswp-width~ and ~data-pswp-height~ to the gallery link from ~image.metadata.width~ / ~image.metadata.height~ in ~src/pages/gallery/[...folder].astro~.
- Add ~data-natural-width~ and ~data-natural-height~ on the ~<Image>~ element using the same metadata dimensions.
- In ~src/scripts/packeryGallery.ts~, resolve dimensions in this order:
  1. link attrs (~data-pswp-width/height~)
  2. img attrs (~data-natural-width/height~)
  3. existing PhotoSwipe itemData values
  4. runtime image dimensions / fallback defaults

** Rule of Thumb
If a lightbox opens a different asset than the thumbnail (or a cropped thumbnail variant), width/height metadata must come from the full asset, never from the layout thumbnail.

* 2025-10-22 - CSS Specificity Beats JavaScript Every Time

** Trigger
Mobile gallery showed persistent gaps between images despite extensive JavaScript fixes (resize handlers, destroying Packery, `!important` in inline styles). Spent hours debugging JavaScript logic when the real issue was CSS.

** Mechanism
CSS rules are *persistent and continuously applied*. JavaScript inline styles are *one-time modifications*. When base CSS defines layout properties without media query overrides:

1. CSS applies rules: `.masonry-item { position: absolute; aspect-ratio: 2/3; }`
2. JavaScript tries to override: `item.style.position = 'relative'`
3. CSS continues to apply its rules throughout page lifecycle
4. Result: CSS wins, gaps remain

Even `element.style.setProperty('position', 'relative', 'important')` in JavaScript can't reliably beat CSS because:
- CSS rules reapply on every render/reflow
- Inline styles are snapshots at execution time
- Browser may prioritize CSS cascade over inline styles in some contexts

** The Real Problem
The codebase had:
- Desktop CSS: `.masonry-item { position: absolute; aspect-ratio: var(--aspect-ratio, 2/3); }`
- Mobile JavaScript: tries to set `position: relative`, `aspect-ratio: auto`
- No CSS media query to override at mobile breakpoint

This created a *specificity war* where JavaScript fought CSS and lost.

** Actionable Insight
*Responsive layout changes belong in CSS media queries, not JavaScript.*

When debugging layout issues:
1. *Check CSS first* - Open DevTools → Computed styles, not just inline styles
2. *Look for missing media queries* - Desktop styles bleeding into mobile/tablet
3. *Use CSS solutions for CSS problems* - Don't try to override CSS with JS
4. *Test with CSS disabled* - Does JS alone fix it? If no, it's a CSS issue

** The Fix
Added CSS media query in `src/pages/index.astro`:

```css
@media (max-width: 768px) {
  .masonry-item {
    position: relative !important;
    aspect-ratio: auto !important;
    width: 100% !important;
    /* ... more overrides ... */
  }
}
```

Result: Instant fix. No JavaScript changes needed beyond the media query.

** Pattern for Future Development
When implementing responsive layouts:
1. Define base desktop styles
2. *Immediately add mobile media query overrides* (don't wait for bugs)
3. Use `!important` judiciously in media queries when fighting specificity
4. Test at all breakpoints before considering the feature "done"

JavaScript should *enhance* CSS layouts, not fight them. If you're destroying DOM nodes or battling inline styles, you're solving the wrong problem.

* 2025-10-03 - Vite Module Imports & Masonry Visibility
- The masonry gallery script was initially imported via a relative path such as ~../scripts/packeryGallery.ts~ inside a regular ~<script type="module">~ block. In Astro + Vite, that executes on the client without bundling, so the browser requested ~/src/scripts/packeryGallery.ts~ and received a 404.
- Because the initializer never ran, masonry items kept their absolute positioning and zero-opacity state, resulting in a blank photo grid—especially visible on mobile where the fallback relies entirely on the script.
- The same bundling rule applies to package imports from page-level scripts. On ~/src/pages/before-after.astro~, PhotoSwipe markup and data attributes were correct, but the lightbox still failed because the page emitted a raw module script containing bare imports like ~photoswipe/lightbox~ instead of a bundled ~/_astro/*.js~ asset.
- Fix: Switch to a hoisted script (~<script hoist>~) so Astro registers the dependency at build time; relative imports like ~import initPackeryGallery from '../scripts/packeryGallery.ts'~ now bundle correctly for every page.
- Reminder: avoid ~Astro.resolve~ for browser-targeted helpers; it runs during SSR and returns plain URLs that bypass Vite's bundler pipeline.
- Checklist update: before shipping a new browser-side helper, confirm the entry point uses ~<script hoist>~ (or a frontmatter import), that a quick ~npm run build~ succeeds without 404s in devtools logs, and that the built HTML references a bundled ~/_astro/*.js~ file rather than leaving bare imports in the page output.

* 2025-10-05 - Masonry Gutters & Edge Balance
- Packery is happiest when column math stays at the canonical 320px + 8px gutter; pushing columns wider without recalculating heights produces the infamous cropped foreheads.
- To get a near edge-to-edge feel without touching Packery internals, wrap the gallery in a ~clamp~-based horizontal padding (see ~.portfolio-wrap~ in ~src/pages/index.astro~). Tuning the clamp keeps large monitors almost full-bleed while still guarding tablets from edge collisions.
- If you *must* widen columns, collect the real aspect ratios (e.g., ahead-of-time via ~sharp~) and set explicit heights before Packery runs, otherwise the forced ~object-fit: cover~ spills important framing.
- Quick test: after tweaking gutters, run ~npm run build~ and flick through the homepage with devtools device toolbar to ensure stacked pairs still align and no gaps appear.

* 2025-10-03 - Mobile Masonry Gaps
- Desktop Packery styles fix explicit heights on `.masonry-item` and images using `!important`. When we flip to the mobile flex fallback, those declarations persisted, so cards kept the desktop height even though the images were set to `auto`, leaving huge blank bands after the visible crop.
- Fix: in the mobile fallback branch (`setupMobileFallback`), explicitly set both the item and `<img>` height via `style.setProperty('height', 'auto', 'important')` and `object-fit: contain` to override the desktop rules with matching specificity.
- Lesson: whenever desktop CSS uses `!important` for layout control, the mobile escape hatch must either remove those classes or override with equal specificity/importance; otherwise expect leftover whitespace or clipping.
- Bonus: Draggabilly is now lazy-loaded through `await import('draggabilly')` inside the helper—pattern to follow for other admin-only libraries.
