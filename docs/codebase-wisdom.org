* 2026-08-22 - The Dev Server Can Serve A Page Whose PhotoSwipe Silently Fails

** Trigger
Clicking any print on the dev homepage did nothing, on the real homepage as well as on a prototype route, while the production build worked. Separately, a Playwright capture of the dev homepage hung for 25 minutes with no output.

** Mechanism
A stale Vite optimize-dep made the dev server answer ~504~ for ~photoswipe.js?v=<hash>~, so the dynamic ~import('photoswipe')~ on click rejected with nothing visible on the page. Reloading does not clear it; restarting the dev server does. The capture hang was ~waitForLoadState('networkidle')~: the homepage's Three.js atmosphere and the HMR socket keep the network busy indefinitely, so ~networkidle~ never arrives.

** Actionable insight
Verify PhotoSwipe against ~npm run build~ output on a static server rather than the dev server, and in Playwright wait for ~load~ plus a fixed settle, never ~networkidle~. If the lightbox dies on every dev page at once, restart the dev server before debugging code.

* 2026-08-19 - Astro 7 Agent Preview And Legacy Hoist Scripts Need Explicit Migration

** Trigger
After the Astro 7 upgrade, Playwright's managed web-server command exited even though an Astro preview child process was serving the site. Once the suite ran against that preview, the Sundance gallery's PhotoSwipe test navigated directly to the image instead of opening the lightbox.

** Mechanism
Astro 7 detects agent environments and backgrounds ~astro preview~ automatically. That ends the parent command Playwright is monitoring even while the detached server remains healthy. Separately, Astro 7 no longer processes the legacy ~<script hoist>~ syntax used by three routes in this repo: the built HTML retained literal ~<script hoist>~ blocks with TypeScript and bare package imports, so the browser could not initialize Packery or PhotoSwipe.

** Actionable insight
For a Playwright-managed Astro 7 preview in an agent environment, prefix the preview command with ~ASTRO_PREVIEW_BACKGROUND=1~ so it remains attached and Playwright owns its lifecycle. Replace legacy ~<script hoist>~ blocks with ordinary Astro-processed ~<script>~ blocks. After either migration, inspect built HTML for literal ~<script hoist>~ tags and bare imports, then browser-test the affected interactive path instead of relying on a successful static build.

* 2026-08-01 - Measuring a Change Requires a Reference That Isolates the Variable

** Trigger
Two measurements during the mobile homepage rebuild produced confident, wrong answers before being caught.

The dev server reported ~886KB~ of JavaScript on the homepage, which would have been reported as a headline performance defect. The production build ships ~54KB~ gzipped; the dev figure is unbundled modules plus the Vite client.

A re-encode of the profile portrait measured ~29.7dB~ PSNR against the shipped file's ~35.3dB~, apparently proving the smaller file was much worse. Raising JPEG quality barely moved the number — it plateaued near ~30dB~ at every quality from 78 to 92, which is not how JPEG behaves.

** Mechanism
The PSNR plateau was the tell. The ground truth had been produced with ImageMagick's resampler while the candidates came from sharp's. The metric was dominated by resampler mismatch, a constant structural difference that no amount of JPEG quality can close. Regenerating the reference with sharp made the numbers behave: ~34.8dB~ at q80 rising to ~38.6dB~ at q92, and mozjpeg q84 reached ~35.4dB~ at 43% of the shipped bytes.

The same class of error nearly recurred when comparing font payloads across two ~astro preview~ servers on different ports. Both serve from the same ~dist/~ directory, so rebuilding for the second measurement silently replaced the first server's content too, and "before" and "after" were the same build.

** Actionable insight
Never quote a bundle size, payload, or asset weight from ~npm run dev~; build and serve ~dist/~ first. When a quality metric refuses to respond to the parameter being swept, suspect the reference rather than the encoder. Generate the reference through the same pipeline as the candidates so the only variable is the one under test. Two ~astro preview~ instances on different ports are not two builds — for a genuine before/after, capture the baseline artefacts to disk while the baseline ~dist/~ exists, then rebuild. Stashing the tree, building, screenshotting, popping, and rebuilding is a reliable way to pixel-diff a "this only changes mobile" claim.

* 2026-08-01 - CSS Grid Auto-Placement Silently Reorders Numbered Content

** Trigger
The homepage photo wall printed its badges ~08, 10, 09~ on a phone. The numbers come from the map index, so the markup order was correct and the defect was purely visual.

** Mechanism
~.photo-wall~ sets ~grid-auto-flow: dense~. At two columns a full-width card cannot fit in the remaining half-slot, so dense packing pulls the *next* card forward to backfill it and defers the full-width card to its own row. Dense packing optimises for holes, and it will reorder to get them — which is invisible when items are interchangeable and glaring when they are numbered.

Separately, a short landscape card beside a tall portrait card left roughly ~200px~ of empty paper, because per-card aspect ratios tuned for a 3-4 column desktop layout produce large height mismatches once only two cards share a row.

** Actionable insight
~grid-auto-flow: dense~ is unsafe wherever items carry a visible sequence — numbers, dates, steps, rankings. Use ~row~ there and remove holes by controlling geometry instead: a uniform media aspect ratio per breakpoint, plus full-width items placed at indices where the preceding half-width items pair off evenly. On this page that is ~nth-child(3)~, ~nth-child(10)~, ~nth-child(17)~ for 17 cards. Also note that GSAP tweening ~rotation~ to ~0~ destroys a deliberate CSS ~transform: rotate()~; read the base angle with ~gsap.getProperty(el, 'rotation')~ and animate around it.

* 2026-07-31 - MDX Feature Variants Need Non-Reserved Metadata and Valid Paragraph Structure

** Trigger
The WikiPortraits feature essay first failed to build when its frontmatter used ~layout: feature~. After renaming that field, several large display paragraphs rendered at ordinary body size while empty elements received the intended classes.

** Mechanism
Astro MDX treats ~layout~ as a reserved frontmatter key and attempts to resolve its value as a layout module. A visual variant named ~layout: feature~ therefore produces a module-resolution error for ~feature~ instead of ordinary collection metadata.

Multiline Markdown content inside an explicit JSX ~<p>~ can compile to a nested paragraph. Because nested ~<p>~ elements are invalid HTML, the browser repairs the DOM into an empty classed paragraph plus unclassed sibling paragraphs. The CSS selector remains attached to the empty element, and grid containers receive unexpected extra children.

** Actionable insight
Use a schema field such as ~presentation~ for content-driven visual variants; reserve ~layout~ for a real Astro/MDX layout import. For multiline prose that needs a display class, use a semantic ~<div>~ wrapper and style its generated child paragraph, or keep the complete text inline inside one explicit ~<p>~. Inspect the rendered children rather than trusting the MDX source when classed prose appears unstyled or a grid has unexplained extra items. Prettier can also emit mixed leading spaces and tabs for nested MDX JSX; after formatting, normalize that indentation and require ~git diff --check~ to pass.

* 2026-07-14 - Responsive Packery Needs Compatible Row Geometry, Not Just Column Geometry

** Trigger
After the cold-load lifecycle race was fixed and the saved order looked clean at five- and six-column test widths, the live homepage still developed large settled holes on a 4200px-wide eight-column viewport. Reordering the new landscape tiles had appeared to solve the narrower checks but did not generalize.

** Mechanism
Packery had a responsive ~columnWidth~ but no ~rowHeight~. CSS generated tile heights from aspect ratios while Packery added a fixed 8px gutter. As columns widened, the outer height of a regular 1-column portrait, a wide 2-column landscape, and a wide-tall 2-column portrait differed by a few pixels from exact 1-row and 2-row multiples. Packery correctly rejected openings that were mathematically too short even though they looked like empty grid cells, producing large holes at some widths.

The hidden ~.grid-sizer~ can define both axes. Giving it ~aspect-ratio: 2 / 3~ and using it as Packery's ~rowHeight~ turns the packing model into responsive grid units: regular is 1 by 1, wide is 2 by 1, and wide-tall is 2 by 2. Because Packery remeasures the sizer during layout, this follows the current CSS width instead of hard-coding a monitor size or maximum column count.

** Actionable insight
When mixed-span Packery tiles are meant to form a modular grid, quantize both axes from the same responsive measurement element. Do not use saved-order changes to disguise geometry drift. Test cold loads on both sides of every responsive breakpoint, include ultrawide widths, and temporarily exercise a future 9- or 10-column rule before declaring the packing contract general. Wait for Packery's transition and reveal stagger to settle before measuring positions; mid-animation rectangles are not final geometry.

* 2026-07-13 - Packery Needs a Full First Layout Before Progressive Image Events

** Trigger
On a cold homepage visit, Packery produced a roughly 20,899px-tall single-column arrangement with giant blank regions. Scrolling or refreshing appeared to fix it, making the newly appended photographs look responsible even though their portrait and landscape classifications were correct.

** Mechanism
The shared initializer used ~initLayout: false~ but did not trigger a full layout after restoring DOM order. Its first Packery operation was ~shiftLayout()~ from an ~imagesLoaded~ progress event. Because ~shiftLayout()~ preserves horizontal positions before Packery had assigned useful ones, items stayed at ~x = 0~ until the all-images callback finally ran ~layout()~. Native lazy loading deferred that callback until scrolling. The page already reserved stable tile geometry with responsive widths and CSS ~aspect-ratio~, so waiting for image pixels was unnecessary.

Packery also captures its internal item list during construction. If the DOM is reordered afterward, call ~reloadItems()~ before the first ~layout()~ so Packery uses that restored order.

** Actionable insight
For Packery pages with reserved tile geometry, use this initialization sequence: restore DOM order, ~reloadItems()~, run one immediate full ~layout()~, then use one ~imagesLoaded~ instance to request animation-frame-coalesced full layouts as images finish and one final safety layout on ~always~. Do not use ~shiftLayout()~ as the first packing pass or call ~fit()~ across every tile during initialization. Diagnose refresh-sensitive blank regions as lifecycle timing before changing photograph classifications or ordering.

* 2026-07-13 - The Legacy Image-Metadata Generator Does Not Cover Current Highlights

** Trigger
Running ~node scripts/generate-image-metadata.js~ after adding selected Packery highlights rewrote ~src/data/image-metadata.json~, regenerated unrelated WebP siblings throughout ~public/~, and modified an existing logo while still omitting the new files under ~src/gallery/highlights/~.

** Mechanism
The script scans only ~public/~, writes WebP derivatives beside every supported image it finds there, and replaces the entire metadata JSON from that obsolete source tree. The current homepage highlight source directory is ~src/gallery/highlights/~, so the generator is not a safe or complete way to register new Packery assets.

** Actionable Insight
Do not run ~scripts/generate-image-metadata.js~ for current Packery additions until it is redesigned around the real source directories and made non-destructive by default. For a small selected set, measure the canonical files directly and add only their ~highlights/<filename>~ dimensions to ~src/data/image-metadata.json~.

* 2026-07-13 - Portable Photo Metadata And Site Visibility Are Separate Layers

** Trigger
Six TIFF 2025 exports had verified embedded titles, captions, keywords, people, and event metadata, but none became visible on the portfolio merely by completing that metadata pass or by considering a Cloudinary upload.

** Mechanism
The current portfolio has distinct consumers:

- Filesystem galleries discover local assets under ~src/gallery/photos/~ and build captions/tags from semantic filenames plus ~tags.json~.
- Red-carpet person pages discover local gallery/highlight files through filename ~match~ patterns and explicit ~photoSlugs~ in ~src/data/people.json~.
- The main Packery homepage reads ~src/data/homepage-images.js~ and serves its selected assets from Cloudinary ~highlights/~ IDs.
- The before/after page imports local assets through ~src/data/beforeAfter.ts~.

ExifTool metadata remains the portable source record and feeds the upload validator, but it does not replace those public routing/configuration layers. The portfolio validator also backfills a missing title from a caption and vice versa, so a passing validation result does not prove a human verified the identity or prose.

** Actionable Insight
Run Exwalker first as the human truth gate, then explicitly choose and wire the destination lane. Do not describe ~uploaded to Cloudinary~, ~metadata complete~, and ~visible on the site~ as the same state. Keep complete galleries local under ~src/gallery/photos/~; reserve Cloudinary for explicitly selected homepage/Packery assets unless the gallery architecture is deliberately migrated.

* 2026-07-08 - Edge-to-Edge Packery Needs Gutter-Aware Fluid Columns

** Trigger
The Photo Wall Packery masonry looked good, but on wider viewports it left a persistent empty band on the right. Earlier attempts to center the whole stage made the grid more balanced but did not actually fill both viewport edges.

** Mechanism
Packery was laying out a full-width container, but the masonry items still used historical fixed widths: 320px regular columns and 648px wide columns with an 8px gutter. Centering, padding, or using ~fitWidth~ can only move that fixed grid; it cannot make the columns consume arbitrary viewport widths.

The fix is to let CSS define fluid item widths that already include gutter math before Packery measures the DOM. For an ~N~-column row with an 8px gutter:

- regular width: ~100% / N - 8px * (N - 1) / N~
- wide width: ~200% / N - 8px * (N - 2) / N~

** Fix
Keep [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/pages/photo-wall.astro][src/pages/photo-wall.astro]] edge-to-edge at the wrapper and item levels:

- ~.portfolio-wrap~ and ~.masonry-items~ stay 100% wide with no horizontal padding.
- Desktop/tablet breakpoints use gutter-aware ~calc()~ widths for ~.grid-sizer~, ~.masonry-item.regular~, ~.masonry-item.wide~, and ~.masonry-item.wide_tall~.
- The same width rules appear in both ~criticalStyles~ and the main inline style block so first paint and settled layout match.
- ~.masonry-items~ keeps ~overflow-x: hidden~ so Packery's staggered first layout cannot expose a temporary horizontal scrollbar while items settle.
- The 768px-and-below mobile fallback stays flex-column and bypasses Packery.

The dedicated configuration note is [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/docs/packery-edge-to-edge-configuration.org][docs/packery-edge-to-edge-configuration.org]].

** Rule of Thumb
If a Packery page has a left/right balance problem, do not start by moving a fixed stage around. First ask whether item widths plus gutters mathematically fill the container. If the page uses critical CSS, update the critical and settled CSS copies together before testing.

When browser-testing the homepage, wait for Packery's staggered first layout to settle before judging overlap or right-edge geometry. Mid-animation rects can briefly look wrong even when the final layout is correct.

* 2026-07-06 - Local PhotoSwipe Failures Can Be Vite Optimized-Dependency Cache Drift

** Trigger
The homepage lightbox opened correctly on [[https://photos.jaydixit.com/][photos.jaydixit.com]] but clicking the same kind of photo on [[http://localhost:4327/][localhost]] did nothing.

** Mechanism
The local dev page had the correct ~portfolio-lightbox~ anchors and PhotoSwipe data attributes, but the browser console showed Vite returning ~504 (Outdated Optimize Dep)~ for ~node_modules/.vite/deps/photoswipe.js~. In that state, the PhotoSwipe dynamic import never resolves, so clicks look like a broken lightbox even though the production bundle is fine.

** Fix
Check the browser console before changing lightbox code. If the error is Vite's outdated optimized dependency for ~photoswipe.js~, force local dependency reoptimization, usually by restarting the dev server or clearing Vite's generated dependency cache. Verify production or a fresh build before treating it as an application regression.

** Rule of Thumb
If PhotoSwipe works in production but not in local dev, first distinguish code failures from Vite dependency-cache failures. A ~504 (Outdated Optimize Dep)~ on ~photoswipe.js~ is a local dev-server artifact, not proof that the shipped lightbox is broken.

* 2026-06-24 - ESLint Flat Config Must Ignore Playwright Artifact Directories Directly

** Trigger
After adding Playwright, a parallel verify run had ~pnpm lint~ fail with an =ENOENT= while ESLint was scanning ~test-results~ as Playwright was creating and cleaning generated artifacts.

** Mechanism
Repo-level =.gitignore= keeps Playwright artifacts out of commits, but the ESLint flat config has its own explicit ignore list. If generated artifact directories are not listed there, ESLint can still walk them during broad commands like ~eslint . --ext .ts,.js,.astro~.

** Fix
Add ~playwright-report/**~ and ~test-results/**~ to the top-level ~ignores~ block in ~eslint.config.js~.

* 2026-07-30 - PhotoSwipe Does Not Bind Escape Until The Opening Animation Ends

** Trigger
The promoted Kinetic homepage lightbox was visibly open and carried ~pswp--open~, but pressing Escape during its longer thumbnail-to-center transition did nothing. Repeated browser probes showed that Escape began working only several seconds later.

** Mechanism
PhotoSwipe 5.4.4 deliberately waits for ~openingAnimationEnd~ before it dispatches ~bindEvents~; its keyboard module registers the document ~keydown~ listener only in response to that event. The root can therefore be visible and marked ~pswp--open~ while Escape is not yet bound. Calling ~pswp.close()~ during the opening transition does not solve this because PhotoSwipe's opener intentionally ignores close requests while ~isOpening~ is true.

** Fix
The shared [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/components/PhotoSwipeLightbox.astro][📄 PhotoSwipe component]] listens for Escape during the opening window and queues one close for ~openingAnimationEnd~. Once the opening completes, PhotoSwipe's normal keyboard listener takes over. This preserves the full opening and closing motion while honoring an early dismissal request.

** Rule of Thumb
Do not infer keyboard readiness from visibility or the ~pswp--open~ class. For a PhotoSwipe interaction that must accept immediate dismissal, queue Escape across the opening transition instead of lengthening tests with an arbitrary sleep or forcing an abrupt destroy.

* 2026-04-27 - Cropped PhotoSwipe Thumbnails Need Explicit Metadata, And Capped Lightbox Images Must Advertise Their Real Max Size

** Trigger
The repo still had a mix of cover-cropped thumbnails, uncapped full-resolution lightbox targets, and lightbox dimensions that described the original image even when the served lightbox source was intentionally capped.

** Mechanism
Two separate PhotoSwipe assumptions were easy to violate:

- If the visible thumbnail uses ~=object-fit: cover=~, PhotoSwipe assumes the preview is *not* cropped unless you set ~=data-cropped="true"=. The open/close animation can feel subtly wrong otherwise.
- If you cap the lightbox source (for example to ~=2200px=~ or ~=2800px=~) or supply ~=data-pswp-srcset=~, then ~=data-pswp-width=~ / ~=data-pswp-height=~ should describe the *largest delivered lightbox image*, not the original full-resolution source.

Using the original dimensions with a capped lightbox still preserves aspect ratio, but it overstates available zoom detail and makes the responsive source metadata less truthful than it should be.

** Fix
- Add ~=data-cropped="true"= anywhere the clickable preview is visibly cropped:
  - ~src/pages/photo-wall.astro~
  - ~src/pages/gallery/[...folder].astro~
  - ~src/components/PhotoGrid.astro~
  - ~src/pages/before-and-after.astro~
- When lightbox sources are capped or responsive, set ~=data-pswp-width=~, ~=data-pswp-height=~, and ~=data-pswp-srcset=~ to match the largest delivered lightbox variant.

** Rule of Thumb
If a PhotoSwipe transition feels "off" from a cover thumbnail, or zoom seems to promise more detail than the slide actually has, check two things first:
- missing ~=data-cropped="true"=
- dimensions that describe the original file instead of the capped lightbox source

* 2026-04-27 - Astro Asset ~=.src= Can Break PhotoSwipe And GLightbox In Dev

** Trigger
Lightbox links built from imported Astro image metadata looked reasonable in source, but opened broken images in development even while the thumbnails themselves still rendered.

** Mechanism
For imported Astro assets, ~=ImageMetadata.src=~ can resolve to a raw =/@fs/...= path in dev. The visible ~<Image>~ often still works because the browser prefers a valid optimized image from ~=srcset=~ or another transformed URL, so the page thumbnail looks healthy.

The trap is that PhotoSwipe or GLightbox opens the anchor ~=href=~, not the browser's chosen ~=currentSrc=~. If the anchor still points at the raw =/@fs/...= path, the lightbox fetch can fail even though the inline image looks fine.

This repo had the risky pattern in:
- ~src/pages/before-and-after.astro~
- ~src/components/PhotoGrid.astro~

** Fix
Generate a served image URL for the lightbox target instead of reusing raw metadata ~=.src=~.

- For Astro-authored asset components, build the lightbox href with ~=getImage()=~
- For DOM-enhanced content images, prefer ~=img.currentSrc || img.src=~ once the image is actually rendered

** Rule of Thumb
If a lightbox image fails in Astro dev but the thumbnail still renders, inspect the anchor ~=href=~ first. If it starts with =/@fs/=, the lightbox target is wrong even if the on-page image looks correct.

* 2026-04-01 - Legacy ~=gallery= Cloudinary Transforms Can Break Otherwise Valid Images

** Trigger
Blog images on ~/blog/nobel-portrait-session/~ were broken even though the underlying Cloudinary public IDs were correct and directly fetchable.

** Mechanism
The shared helper in ~src/lib/cloudinary.ts~ was still honoring ~=PUBLIC_CLOUDINARY_TRANSFORM=gallery~ and generating URLs like ~.../image/upload/t_gallery,w_1600/...~.

That named transform no longer exists on Cloudinary, so requests fail with ~=Unknown transformation gallery=~. This is easy to miss because the public ID itself is valid, and swapping only the transformation string to ~f_auto,q_auto,w_1600~ immediately makes the same asset load.

The bug is worse than a single broken page because blog hero images, related-post cards, and any helper-generated Cloudinary URL all inherit the same transform logic.

** Fix
Treat the legacy ~=gallery=~ value as invalid and fall back to explicit transforms instead of blindly emitting ~t_gallery~.

- In ~src/lib/cloudinary.ts~, default to ~f_auto,q_auto~ when ~=PUBLIC_CLOUDINARY_TRANSFORM=~ is missing or still set to ~=gallery=~
- In MDX posts that hardcode old Cloudinary URLs, replace ~t_gallery,...~ with explicit transforms such as ~f_auto,q_auto,w_1600~
- Verify suspicious Cloudinary failures with ~curl -I~; if the same public ID loads under ~f_auto,q_auto~ but not ~t_gallery~, the transform is the problem, not the asset

** Rule of Thumb
Treat named Cloudinary transforms as external configuration that can drift or disappear. If a page breaks but the public ID is valid, test the same asset with explicit ~f_auto,q_auto~ transforms before assuming the image is missing.

* 2026-04-01 - Blog Post Images Need Template-Level PhotoSwipe Wiring

** Trigger
Images on ~/blog/nobel-portrait-session/~ rendered correctly but clicking them did nothing, even after the broken image URLs themselves were fixed.

** Mechanism
Blog post body content is rendered from Markdown/MDX as plain ~<img>~ tags inside ~src/pages/blog/[slug].astro~. Unlike gallery pages or ~/before-and-after/~, those images are not authored with PhotoSwipe wrappers, dimensions, or captions.

That means there is nothing for PhotoSwipe to attach to unless the blog template itself enhances the rendered images. Fixing one post by hand would just move the bug around to the next essay.

** Fix
Handle blog-image lightbox behavior in the shared blog post template, not in individual posts.

- Give the article a stable gallery container
- Wrap rendered blog-body and hero images in ~=portfolio-lightbox=~ anchors at runtime if they are not already linked
- Populate ~=data-pswp-width=~, ~=data-pswp-height=~, and ~=data-pswp-caption=~ from the image element
- Initialize PhotoSwipe from a hoisted script so Astro bundles the code into ~/_astro/*.js~

** Rule of Thumb
If content comes from Markdown/MDX, assume it will emit plain HTML. Cross-cutting behavior like PhotoSwipe belongs in the page template or renderer pipeline, not in individual content files.

* 2026-03-31 - Homepage Cloudinary IDs Can Drift From Local Highlight Filenames

** Trigger
Local highlight files were renamed to cleaner subject-based names such as ~jude-law_tiff.jpg~ and ~ron-livingston_sxsw-office-space-event_2024.jpg~, but the landing page started serving broken Cloudinary URLs.

** Mechanism
The homepage derives Cloudinary public IDs from ~=filename=~ in ~src/data/homepage-images.js~. That works only if the remote Cloudinary asset was uploaded under the same basename.

Once a local file is renamed without also renaming or re-uploading the Cloudinary asset, the landing page starts requesting a public ID that does not exist, even though the local file and metadata are correct.

** Fix
Allow homepage entries to carry an explicit ~=cloudinaryPublicId=~ override and fall back to the filename-derived ID only when local and remote names still match.

- Keep canonical local filenames meaningful in ~/src/gallery/highlights/~
- In ~/src/data/homepage-images.js~, set ~=cloudinaryPublicId=~ when the Cloudinary asset still lives under an older name
- In ~/src/pages/photo-wall.astro~, prefer ~=cloudinaryPublicId=~ over the derived ~=highlights/{basename}=~ pattern

** Rule of Thumb
Treat Cloudinary public IDs as external identifiers, not as guaranteed mirrors of local filenames. If a local rename happens after upload, either rename the Cloudinary asset too or add an explicit override in homepage data.

* 2026-03-31 - Sibling Source WebP Files Must Be Excluded From Gallery-Style Source Lists

** Trigger
Routes like ~/gallery/events/nobel/~ and the gallery index surfaced duplicate photos because both ~.jpg~ and sibling source ~.webp~ files were being treated as separate source images.

** Mechanism
Under ~/src/gallery/photos/~, source ~.webp~ files are derivative siblings of canonical source images, not distinct photos. Routes that count or list raw files by folder, such as ~src/pages/gallery/index.astro~, ~src/pages/gallery/[...folder].astro~, and ~src/pages/upload-to-commons.astro~, will overcount and duplicate cards if they glob ~=webp=~ alongside ~jpg/jpeg/png/gif~.

Routes that dedupe by slug can safely continue to glob ~.webp~, but gallery-style source-list pages should not.

** Fix
Exclude ~.webp~ from raw gallery photo globs on routes that build folder counts, source-photo lists, or upload queues.

- Use patterns like ~**/*.{jpg,jpeg,png,gif}~ for folder galleries, gallery indexes, and Commons upload helpers
- Keep ~.webp~ only on routes that intentionally dedupe by slug and source priority

** Rule of Thumb
If a route is treating files as source photos rather than as renderable asset variants, do not glob sibling ~.webp~ files.

* 2026-03-31 - Portrait Pages Need Explicit Photo Mappings For Group Shots And Legacy Filenames

** Trigger
Portrait pages initially worked only when the filename started with the subject slug, which left highlight-only people, group portraits, and event-style filenames invisible or stuck on ~/404~ pages.

** Mechanism
The original portraits matcher only looked at the subject slug, defined as the part of the filename before the first ~=_=. That works for files like ~dave-franco_sundance_2025.jpg~, but it fails for cases like:

- ~group-portrait_ana-de-armas-sydney-sweeney-ron-howard_2024.jpg~
- ~2024-03-09_SXSW_Conan_Nick-Kroll_Office-Space_events_07141.jpg~
- legacy highlight filenames that do not begin with the person slug

Highlight-only pages also need the underlying image files to exist locally in ~/src/gallery/highlights/~. Metadata entries in ~src/data/homepage-images.js~ and ~src/data/image-metadata.json~ are not enough by themselves.

** Fix
Keep the simple ~=match= prefix logic for normal filenames, but add explicit ~=photoSlugs= overrides in ~/src/data/people.json~ for exceptions.

- Portrait routes should scan both ~/src/gallery/photos/~ and ~/src/gallery/highlights/~
- Exact ~=photoSlugs= matches should be checked before prefix-based subject matching
- Person-page captions should reuse homepage captions from ~/src/data/homepage-images.js~ when available, especially for group shots and event-style filenames
- If a portrait page is backed only by highlights, render the card without forcing a broken gallery detail link

** Rule of Thumb
If a person is visible on the site but their filename does not cleanly start with their slug, do not invent more filename parsing. Add an explicit ~=photoSlugs= mapping and make sure the corresponding file exists locally.

* 2026-02-18 - PhotoSwipe Can Distort If It Uses Cropped Thumbnail Dimensions

** Trigger
On gallery folder pages (example: ~/gallery/events/nobel~), images opened in PhotoSwipe looked squeezed/distorted even though thumbnails looked fine.

** Mechanism
Masonry thumbnails are rendered with heuristic crop sizes (~320x480~, ~648x480~, etc.) for layout, but PhotoSwipe was using those thumbnail dimensions to calculate slide ratio while loading the full image.

If PhotoSwipe receives the crop dimensions instead of the full source dimensions, slide geometry is wrong and images appear stretched.

** Fix
Always pass true source dimensions to PhotoSwipe, not masonry crop dimensions:

- Add ~data-pswp-width~ and ~data-pswp-height~ to the gallery link from ~image.metadata.width~ / ~image.metadata.height~ in ~src/pages/gallery/[...folder].astro~.
- Add ~data-natural-width~ and ~data-natural-height~ on the ~<Image>~ element using the same metadata dimensions.
- In ~src/scripts/packeryGallery.ts~, resolve dimensions in this order:
  1. link attrs (~data-pswp-width/height~)
  2. img attrs (~data-natural-width/height~)
  3. existing PhotoSwipe itemData values
  4. runtime image dimensions / fallback defaults

** Rule of Thumb
If a lightbox opens a different asset than the thumbnail (or a cropped thumbnail variant), width/height metadata must come from the full asset, never from the layout thumbnail.

* 2025-10-22 - CSS Specificity Beats JavaScript Every Time

** Trigger
Mobile gallery showed persistent gaps between images despite extensive JavaScript fixes (resize handlers, destroying Packery, `!important` in inline styles). Spent hours debugging JavaScript logic when the real issue was CSS.

** Mechanism
CSS rules are *persistent and continuously applied*. JavaScript inline styles are *one-time modifications*. When base CSS defines layout properties without media query overrides:

1. CSS applies rules: `.masonry-item { position: absolute; aspect-ratio: 2/3; }`
2. JavaScript tries to override: `item.style.position = 'relative'`
3. CSS continues to apply its rules throughout page lifecycle
4. Result: CSS wins, gaps remain

Even `element.style.setProperty('position', 'relative', 'important')` in JavaScript can't reliably beat CSS because:
- CSS rules reapply on every render/reflow
- Inline styles are snapshots at execution time
- Browser may prioritize CSS cascade over inline styles in some contexts

** The Real Problem
The codebase had:
- Desktop CSS: `.masonry-item { position: absolute; aspect-ratio: var(--aspect-ratio, 2/3); }`
- Mobile JavaScript: tries to set `position: relative`, `aspect-ratio: auto`
- No CSS media query to override at mobile breakpoint

This created a *specificity war* where JavaScript fought CSS and lost.

** Actionable Insight
*Responsive layout changes belong in CSS media queries, not JavaScript.*

When debugging layout issues:
1. *Check CSS first* - Open DevTools → Computed styles, not just inline styles
2. *Look for missing media queries* - Desktop styles bleeding into mobile/tablet
3. *Use CSS solutions for CSS problems* - Don't try to override CSS with JS
4. *Test with CSS disabled* - Does JS alone fix it? If no, it's a CSS issue

** The Fix
Added CSS media query in `src/pages/photo-wall.astro`:

```css
@media (max-width: 768px) {
  .masonry-item {
    position: relative !important;
    aspect-ratio: auto !important;
    width: 100% !important;
    /* ... more overrides ... */
  }
}
```

Result: Instant fix. No JavaScript changes needed beyond the media query.

** Pattern for Future Development
When implementing responsive layouts:
1. Define base desktop styles
2. *Immediately add mobile media query overrides* (don't wait for bugs)
3. Use `!important` judiciously in media queries when fighting specificity
4. Test at all breakpoints before considering the feature "done"

JavaScript should *enhance* CSS layouts, not fight them. If you're destroying DOM nodes or battling inline styles, you're solving the wrong problem.

* 2025-10-03 - Vite Module Imports & Masonry Visibility
- The masonry gallery script was initially imported via a relative path such as ~../scripts/packeryGallery.ts~ inside a regular ~<script type="module">~ block. In Astro + Vite, that executes on the client without bundling, so the browser requested ~/src/scripts/packeryGallery.ts~ and received a 404.
- Because the initializer never ran, masonry items kept their absolute positioning and zero-opacity state, resulting in a blank photo grid—especially visible on mobile where the fallback relies entirely on the script.
- The same bundling rule applies to package imports from page-level scripts. On ~/src/pages/before-and-after.astro~, PhotoSwipe markup and data attributes were correct, but the lightbox still failed because the page emitted a raw module script containing bare imports like ~photoswipe/lightbox~ instead of a bundled ~/_astro/*.js~ asset.
- Fix: Switch to a hoisted script (~<script hoist>~) so Astro registers the dependency at build time; relative imports like ~import initPackeryGallery from '../scripts/packeryGallery.ts'~ now bundle correctly for every page.
- Reminder: avoid ~Astro.resolve~ for browser-targeted helpers; it runs during SSR and returns plain URLs that bypass Vite's bundler pipeline.
- Checklist update: before shipping a new browser-side helper, confirm the entry point uses ~<script hoist>~ (or a frontmatter import), that a quick ~npm run build~ succeeds without 404s in devtools logs, and that the built HTML references a bundled ~/_astro/*.js~ file rather than leaving bare imports in the page output.

* 2025-10-05 - Masonry Gutters & Edge Balance
- Packery is happiest when column math stays at the canonical 320px + 8px gutter; pushing columns wider without recalculating heights produces the infamous cropped foreheads.
- To get a near edge-to-edge feel without touching Packery internals, wrap the gallery in a ~clamp~-based horizontal padding (see ~.portfolio-wrap~ in ~src/pages/photo-wall.astro~). Tuning the clamp keeps large monitors almost full-bleed while still guarding tablets from edge collisions.
- If you *must* widen columns, collect the real aspect ratios (e.g., ahead-of-time via ~sharp~) and set explicit heights before Packery runs, otherwise the forced ~object-fit: cover~ spills important framing.
- Quick test: after tweaking gutters, run ~npm run build~ and flick through the homepage with devtools device toolbar to ensure stacked pairs still align and no gaps appear.

* 2025-10-03 - Mobile Masonry Gaps
- Desktop Packery styles fix explicit heights on `.masonry-item` and images using `!important`. When we flip to the mobile flex fallback, those declarations persisted, so cards kept the desktop height even though the images were set to `auto`, leaving huge blank bands after the visible crop.
- Fix: in the mobile fallback branch (`setupMobileFallback`), explicitly set both the item and `<img>` height via `style.setProperty('height', 'auto', 'important')` and `object-fit: contain` to override the desktop rules with matching specificity.
- Lesson: whenever desktop CSS uses `!important` for layout control, the mobile escape hatch must either remove those classes or override with equal specificity/importance; otherwise expect leftover whitespace or clipping.
- Bonus: Draggabilly is now lazy-loaded through `await import('draggabilly')` inside the helper—pattern to follow for other admin-only libraries.

* 2026-08-22 - Reload ~CLOUDINARY_URL~ After Dotenv Instead Of Passing It As A Config Field

The simple Cloudinary uploader loaded the repo’s ~CLOUDINARY_URL~ with dotenv, then called ~cloudinary.config({ cloudinary_url: process.env.CLOUDINARY_URL })~. The installed Node SDK does not parse a ~cloudinary_url~ config field, so Admin API calls failed with ~Must supply cloud_name~ even though the complete URL was present.

After dotenv has populated the environment, call ~cloudinary.config(true)~ to make the SDK parse ~CLOUDINARY_URL~, then apply optional settings such as ~secure: true~ in a second ~cloudinary.config~ call. This was verified by uploading and reading back ~highlights/alexander-skarsgard_nyff_2025~ with its expected 2000 by 3000 dimensions.

* 2026-08-22 - Prettier MDX Output Can Trigger Git’s Space-Before-Tab Check

Prettier’s MDX printer can combine Markdown’s space indentation with tabs used for embedded JSX. This still happens with ~useTabs: false~ and passes ~prettier --check~, but Git reports “space before tab in indent.” Post-processing the tabs makes Git happy but causes Prettier to reject the file.

Keep Prettier’s canonical output and add ~*.mdx whitespace=-space-before-tab~ to ~.gitattributes~. This disables only that incompatible Git check for MDX while leaving every other whitespace check active.

* 2026-08-23 - Commons Gallery Albums Reference Wikimedia Commons Files

** Trigger
An album URL looks like a direct photo-upload destination, but its editor operates on existing Wikimedia Commons files.

** Mechanism
Commons Gallery does not host a separate media copy. An editor adds media by Commons filename after the file exists on Wikimedia Commons, then controls album ordering and album-specific captions.

** Actionable insight
Treat a Commons Gallery destination as a two-stage publication: upload and verify the file on Wikimedia Commons first, then use the authenticated album editor’s ~Manage Media~ → ~Add by Filename~ flow. Preserve the album URL and Commons filename in the publication receipt so the browser step is resumable.

* 2026-08-23 - A Commons New Version Is Not A New Upload With A Reused Name

** Trigger
A corrected photograph should replace the current binary revision while keeping its established Commons page, categories, history, and transclusions.

** Mechanism
Pywikibot's ~UploadRobot~ is oriented around creating a file and assigning description text. For a replacement, use the exact existing ~FilePage~ and upload the new binary with an edit comment while allowing only the expected ~exists~ warning. Query the live revision before and after; filename existence alone cannot prove that the replacement happened.

** Actionable insight
Model ~new~ and ~new-version~ as distinct publication modes. A replacement must preflight an existing exact target, leave page text alone, record the previous revision checksum, and succeed only when the verified live checksum changes.

* 2026-08-23 - Pywikibot Login Can Block Invisibly Under A Capturing Parent

** Trigger
The approved Commons executor appeared silent for more than two minutes after launching Pywikibot.

** Mechanism
The Pywikibot process had completed its network request and was blocked reading interactive login input. Execa was capturing its output, so the credential prompt was not visible. The Commons API confirmed that no new revision had been created.

** Actionable insight
Run the Pywikibot adapter with stdin ignored and a finite timeout. If no noninteractive credential is configured, fail closed and use Jay's authenticated Commons browser session after the same reviewed plan and action-time approval; never start a second upload while the first process is still alive.
