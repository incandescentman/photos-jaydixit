* Core Philosophy

** Content First, Code Adapts
Photography content is the source of truth:
- **Photos drive the structure** - folder organization determines galleries
- **Metadata in filenames** - captions extracted from filenames
- **Code serves content** - parsers and generators adapt to photo organization
- **Preserve photographer intent** - don't modify photos or organization to fix code

** Static Generation with Dynamic Feel
- Pre-rendered galleries for speed
- Progressive enhancement for interactivity
- Cloudinary for optimization
- Minimal JavaScript for core functionality

** Project Structure

*** Core Directories
- **~/src/gallery/photos/~** - Photo storage organized by gallery
- **~/src/gallery/highlights/~** - Canonical local highlight files used by homepage and portrait pages
- **~/src/pages/~** - Astro pages and routes
- **~/src/components/~** - Reusable UI components
- **~/src/lib/~** - Utilities and helpers (including cloudinary.ts)
- **~/docs/~** - Documentation (this directory)

*** Key Files
- **~site.config.mts~** - Site configuration
- **~astro.config.mts~** - Astro configuration
- **~src/data/homepage-images.js~** - Homepage image configuration
- **~src/data/people.json~** - Portraits manifest (person slugs, names, match patterns, bios, Wikipedia links)
- **~src/lib/cloudinary.ts~** - Cloudinary URL helpers
- **~scripts/upload-to-cloudinary.js~** - Upload images to Cloudinary
- **~vercel.json~** - Deployment configuration

** Key Invariants

*** PhotoSwipe Is Mandatory Site-Wide
- *Every page that displays photographs must have working PhotoSwipe for every photograph.* This includes homepages, galleries, person pages, editorial and story pages, blog posts, About pages, comparison pages, and experimental routes.
- Never replace a PhotoSwipe-enabled photograph with a plain image or ordinary image link while changing copy, layout, or image sources.
- A page change involving photographs is not complete until browser verification confirms that the first click opens the correct full-size image, navigation works when the page contains multiple photographs, and Escape closes the lightbox.
- Verify PhotoSwipe at desktop and mobile widths and check for browser errors. A successful build alone does not prove that the lightbox works.

*** Content Organization
- Photos organized in `src/gallery/photos/[gallery-name]/` folders
- Each folder becomes a gallery page
- Metadata extracted from filenames or tags.json
- The canonical ingest workflow is: Lightroom export → human review with [[file+emacs:/Users/jay/Dropbox/github/exwalker][Exwalker]] → Exwalker readiness audit → semantic publication filename → local gallery/person/highlight wiring → portfolio validation and rendered preview
- Embedded EXIF/IPTC/XMP is the portable source record, but live gallery captions and public person routing come from filenames, ~tags.json~, and ~src/data/people.json~
- ~scripts/photo-cli.js~ validates merged EXIF/IPTC/XMP plus ~tags.json~ and supports intentional Cloudinary album uploads; validator success proves field presence, not factual identity or caption truth
- Never modify photo organization to fix code issues

*** Cloudinary Integration (Homepage)
- Homepage images served directly from Cloudinary CDN
- No build-time image processing for homepage
- URL pattern: `https://res.cloudinary.com/dszpm7yps/image/upload/f_auto,q_auto,w_{width}/highlights/{publicId}`
- Automatic format negotiation (AVIF/WebP/JPEG)
- Images uploaded via `scripts/upload-to-cloudinary.js`
- Cloudinary is selective in the current architecture: use it for Jay-approved homepage/Packery highlights and other explicit Cloudinary consumers, not as a required mirror of every filesystem gallery photograph
- Files under ~src/gallery/photos/~ are the canonical source for public filesystem galleries and are processed by Astro/Vercel without a Cloudinary upload
- Canonical local highlight source files live in `src/gallery/highlights/` and should stay meaningfully named
- When a local highlight filename no longer matches the remote Cloudinary asset name, set ~=cloudinaryPublicId=~ in ~src/data/homepage-images.js~ instead of forcing an immediate Cloudinary rename
- Do not rely on the legacy named transform ~=gallery=~. The safe default in ~src/lib/cloudinary.ts~ is explicit ~f_auto,q_auto~ transforms.

*** Build Process
- Static generation for all gallery pages
- Content collections for photo metadata
- Dynamic imports for lightbox functionality
- Progressive image loading
- Blog post images are rendered from Markdown/MDX as plain ~<img>~ tags and are enhanced into PhotoSwipe links by ~src/pages/blog/[slug].astro~, not by the content files themselves

*** Vercel Deployment
- Production hosting is Vercel Git integration for [[https://photos.jaydixit.com][photos.jaydixit.com]].
- [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/vercel.json][vercel.json]] is the deployment contract: ~framework~ is ~astro~, ~installCommand~ is ~pnpm install~, ~buildCommand~ is ~pnpm build~, and ~outputDirectory~ is ~dist~.
- [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/astro.config.mts][astro.config.mts]] sets ~output: 'static'~ and ~site: 'https://photos.jaydixit.com'~.
- Pushing [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/][this repo]]'s ~main~ branch to ~origin~ should trigger a Vercel production deploy when the GitHub integration is connected. Because Vercel deploy quotas are limited, do not push unless Jay explicitly says ~push~.
- Local verification should use ~pnpm build~ and, when needed, ~pnpm exec astro preview~ or the Playwright e2e suite, which builds and previews the static output itself.

*** Performance
- Lazy loading for images
- Homepage and folder-page masonry use deliberate Packery progressive enhancement on desktop/tablet, with a flex-column mobile fallback
- Minimal client-side JavaScript
- Cloudinary for automatic optimization

** Quick Reference

*** To add a new gallery:
1. Create folder in `src/gallery/photos/[gallery-name]/`
2. Add photos to folder
3. Create `tags.json` for gallery metadata (optional)
4. Run build to generate gallery page
5. Test gallery at `/gallery/[gallery-name]`

*** To avoid duplicate gallery photos:
1. Treat sibling ~.webp~ files in ~src/gallery/photos/~ as derivative assets, not separate source photos
2. On gallery-style source-list routes, use glob patterns like ~**/*.{jpg,jpeg,png,gif}~ rather than including ~webp~
3. If a route intentionally keeps ~webp~ in its glob, it must dedupe by slug/source priority before rendering counts or cards

*** To add a portrait (person page):
1. Ensure a solo photo of the person exists in any gallery or highlights folder (filename must start with subject slug, e.g. =ray-kurzweil_event_2024.jpg=)
2. Add an entry to =src/data/people.json=:
   #+begin_src json
   {
     "slug": "ray-kurzweil",
     "name": "Ray Kurzweil",
     "match": ["ray-kurzweil"],
     "bio": "Inventor, author, and futurist",
     "wikipedia": "https://en.wikipedia.org/wiki/Ray_Kurzweil"
   }
   #+end_src
3. The =match= array controls which filenames map to this person (matches the subject slug, i.e. the part before the first =_= in the filename). For example, =["dave-franco"]= matches =dave-franco_sundance_2025.jpg=.
4. For group shots and non-standard filenames, use =photoSlugs= for explicit file-to-person mapping. These appear on person pages but not the index.
5. Build/dev to generate the page at =/red-carpet/ray-kurzweil=
6. The person appears on the =/red-carpet/= index only if they have at least one solo photo (matched by =match= pattern, with no other person's slug in the filename). People with only group shots or =photoSlugs= have person pages but are excluded from the index.
7. Legacy =/portraits/= URLs now redirect to =/red-carpet/= and should be treated as compatibility paths, not the primary public route.
8. Bio guidelines: omit bio for household names. Use achievement-first descriptors for less recognizable people (e.g., "Nobel Prize-winning physicist"). Avoid generic labels like "Actor".

*** To modify gallery layout:
1. Check [[file:design-architecture.org::*Masonry Layout][design-architecture.org::*Masonry Layout]] first
2. Modify CSS in layout component
3. Test responsive behavior
4. Verify lazy loading still works
5. Check build time impact

*** To debug Cloudinary issues:
1. Check [[file:codebase-wisdom.org][codebase-wisdom.org]] for similar issues
2. Verify API credentials in `.env`
3. Check content layer sync logs
4. Test URL transformations manually
5. Clear API cache if needed

*** To fix a bug:
1. Search [[file:codebase-wisdom.org][codebase-wisdom.org]] for similar issues
2. Load full context of related files
3. Test fix locally
4. Update codebase-wisdom.org with findings
