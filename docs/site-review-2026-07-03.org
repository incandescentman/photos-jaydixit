Full review of the live site (https://photos.jaydixit.com) plus a two-agent codebase audit (design layer + technical layer). Organized by priority, with implementation suggestions for each item.

Live-site observations were made in Chrome on 2026-07-03: gray placeholder boxes for 3–5+ seconds on [[https://photos.jaydixit.com/red-carpet/][/red-carpet/]], [[https://photos.jaydixit.com/gallery/][/gallery/]], person pages, and [[https://photos.jaydixit.com/before-after][/before-after]]; homepage masonry visibly re-laying-out during load with horizontal overflow.

* 🔥 Tier 1 — High-impact fixes (visitor-facing)

** DONE Compress the 5.7 MB logo.png
The single highest-leverage fix on the site.

- *Problem*: [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/public/logo.png][📄 public/logo.png]] is 5,746,187 bytes — a 2048×2048 PNG rendered at 56px in the nav. It loads on *every page* and saturates the connection while photo thumbnails queue behind it. This is the main cause of the "gray boxes for seconds" experience.
- *Verified*: ~curl -s -o /dev/null -w '%{size_download}' https://photos.jaydixit.com/logo.png~ → 5746187 bytes. Photo thumbnails themselves are only 30–55 KB.
- *Completed 2026-07-04*: [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/public/logo-nav.webp][📄 public/logo-nav.webp]] is now the nav asset, [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/public/logo-large.webp][📄 public/logo-large.webp]] is now the modal asset, and the original PNG lives at [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/assets/logo-original.png][📄 src/assets/logo-original.png]] so ~/logo.png~ is no longer publicly served.
- *Implementation*:
  1. Generate small derivatives with sharp (already a dev dependency):
     ~npx sharp-cli~ or a tiny node script: resize to 112px (2x of 56px display) and 512px (for the logo modal), export as webp.
     #+begin_src bash
     node -e "const s=require('sharp'); s('public/logo.png').resize(112).webp({quality:85}).toFile('public/logo-nav.webp'); s('public/logo.png').resize(512).webp({quality:85}).toFile('public/logo-large.webp')"
     #+end_src
  2. Update the two ~<img src="/logo.png">~ references in [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/components/NavBar.astro][📄 NavBar.astro]] (nav logo → ~logo-nav.webp~, zoom modal → ~logo-large.webp~).
  3. Keep the original PNG out of ~public/~ (move to ~src/assets/~ or delete) so it can't be served again.
- *Expected result*: ~5.7 MB → ~10–30 KB per page load.

** TODO Make above-the-fold images eager / prioritized
- *Problem*: every image site-wide is ~loading="lazy"~, including the homepage LCP images (~src/pages/index.astro:701, :726, :783~). First paint shows gray placeholder boxes.
- *Implementation*:
  - Homepage: for the first N items (say, the first 4–6 in the masonry order), emit ~loading="eager" fetchpriority="high"~; keep ~lazy~ for the rest. The render loop already has the index available.
  - Index pages ([[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/pages/red-carpet/index.astro][📄 red-carpet/index.astro]], [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/pages/gallery/index.astro][📄 gallery/index.astro]]): same treatment for the first row of cards.
  - Optionally add ~<link rel="preload" as="image">~ for the known LCP image in the head slot.

** TODO Replace the homepage Packery masonry with a deterministic layout
- *Problem*: while loading, the homepage shows large blank regions; images pop into place one at a time as Packery re-lays-out; the grid overflows the viewport horizontally (horizontal scrollbar); even settled there's an empty region at bottom-right. The ~300-line custom "gap optimizer" (~src/pages/index.astro:90–381~) fights the layout engine.
- *Implementation options* (pick one):
  1. /Recommended:/ ~justified-layout~ (Flickr's algorithm — *already in package.json*). Compute row-based layout at build time in the frontmatter using the known aspect ratios from [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/data/image-metadata.json][📄 image-metadata.json]], emit absolutely-positioned items with inline ~top/left/width/height~. Zero client JS, zero CLS, no gaps by construction. PhotoSwipe still works unchanged.
  2. CSS Grid with ~grid-template-rows: masonry~ is still not cross-browser; skip.
  3. Plain CSS columns (like ~Gallery.astro~) — simplest, but loses left-to-right visual ordering.
- Once replaced, delete Packery, imagesloaded, draggabilly, and the gap-optimizer code. See also [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/docs/masonry-architecture-improvements.org][📄 masonry-architecture-improvements.org]] for earlier thinking on this.

* ⚙️ Tier 2 — Infrastructure & integrity

** TODO Fix or delete the broken GitHub Actions
- *Problem*: all three workflows in [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/.github/workflows/][📁 .github/workflows/]] run ~npm ci~, but the repo is pnpm-only (no ~package-lock.json~) — they cannot succeed. ~deploy.yml~ also still deploys ~dist~ to GitHub Pages even though production is Vercel Git integration.
- *Implementation*:
  1. Delete ~deploy.yml~ (Vercel already handles deploys).
  2. In ~test.yml~ / ~quality.yml~: use ~pnpm/action-setup~ + ~actions/setup-node~ with ~cache: pnpm~, then ~pnpm install --frozen-lockfile~ and ~pnpm test~ / ~pnpm lint~.
  3. Pin Node: add ~"engines": { "node": "22.x" }~ to package.json or an ~.nvmrc~, and use the same version in CI and Vercel.

** TODO Verify and document Supabase RLS on photo_user_likes
- *Problem*: [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/components/PhotoLikeButton.astro][📄 PhotoLikeButton.astro]] inserts/deletes rows client-side keyed on a localStorage ~visitor_id~. No RLS policies are committed or documented anywhere in the repo. Unless RLS is locked down in the Supabase dashboard, anyone can forge or delete likes and manipulate /popular.
- *Implementation*:
  1. In the Supabase dashboard, confirm policies on ~photo_user_likes~: public ~SELECT~; ~INSERT~ allowed only with a ~unique(photo_id, visitor_id)~ constraint; ~DELETE~ restricted to rows matching the caller's own ~visitor_id~ (or disallowed entirely — accept that "unlike" only works via a soft client-side state).
  2. Commit the actual SQL (schema + policies) to a new ~supabase/schema.sql~ in the repo so it's documented and reproducible.
  3. Accept the residual risk: anonymous likes can never be fully tamper-proof without auth; the goal is raising the bar from "trivially scriptable" to "annoying."

** TODO Fix the unbounded /popular likes query
- *Problem*: ~src/pages/popular.astro:267~ fetches *every like row ever* (~select('photo_id')~) and counts client-side; it also renders a card for every photo on the site and hides zero-like ones in JS.
- *Implementation*: create a Postgres view or RPC in Supabase (~select photo_id, count(*) from photo_user_likes group by photo_id order by count desc limit 50~) and call that instead. Render only photos that have likes.

* 🎨 Tier 3 — Design-system consolidation

** TODO Unify typography (one source of truth)
- *Problem*: [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/styles/global.css][📄 global.css]] sets Karla body + Cormorant Garamond headings, while [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/tailwind.config.js][📄 tailwind.config.js]] maps ~font-sans~ → Inter and declares Playfair Display (never loaded, never used). Result: /gallery/ headings are serif, /red-carpet/ is bold Inter, and /about + /before-after mix serif, Inter, and inline ~system-ui~ on the same page.
- *Recommendation*: keep the Cormorant Garamond + Karla pairing (distinctive, editorial, suits a photo portfolio) and eliminate Inter.
- *Implementation*:
  1. In tailwind.config.js: set ~sans: ['Karla', ...]~ and ~serif: ['Cormorant Garamond', ...]~; delete the Playfair entry.
  2. Sweep pages for ~font-sans~ / ~font-black~ on headings (about.astro:10/91/99, red-carpet/index.astro:183/207/220, before-after.astro:93) and remove the overrides so headings inherit the global serif.
  3. Remove the inline ~system-ui~ stacks in before-after.astro (~:298–320~).
  4. Kill duplicate font loading: Dancing Script is loaded twice (global.css:2 and MainLayout.astro:114–117); NavBar injects its own preconnect + Inter stylesheet (NavBar.astro:18–23). Load all fonts once in MainLayout. Consider self-hosting via ~@fontsource~ packages to remove the render-blocking Google Fonts round-trip entirely.
  5. Check weights: ~font-black~ (900) is used but Karla loads only up to 800 — either load the weight or step down to ~font-bold~.

** TODO Define a single accent color token

* ✨ Tier 5 — Feature ideas

** TODO Homepage: tell the WikiPortraits story
The site's most distinctive hook — "I photograph celebrities so Wikipedia can have better photos" — is invisible on the homepage: no headline, no ~<h1>~, no intro line.
- *Implementation*: a single editorial block above the grid: an ~<h1>~ ("Jay Dixit — Red Carpet Photography for Wikipedia" or similar), one sentence of context, and a small "See the Before & After →" link. Keep it minimal so the photos stay dominant. This also fixes the missing-h1 accessibility issue.

** TODO Search on the entry pages
Filtering exists on gallery folder pages, but the homepage and /red-carpet/ (the real entry points) have none.
- *Implementation*: a single client-side search box on /red-carpet/ filtering the person cards by name/event (the data is already in the DOM; ~30 lines of JS). Optionally the same for homepage captions.

** TODO Populate albums
[[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/content/albums/][📁 src/content/albums/]] is scaffolded but empty. Curated sets ("TIFF 2024", "Nobel Laureates", "SXSW") make better shareable URLs than raw folders. Already noted in CLAUDE.org future tasks.

** TODO Photo detail pages: provenance block
Turn each photo page into a small proof of the WikiPortraits mission: which Wikipedia article uses the image, the license badge (CC BY-SA), and a "View on Wikimedia Commons" link. Data could live in a per-folder json (like tags.json) or extend [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/data/people.json][📄 people.json]] with a ~commonsUrl~ field.

** TODO Content tasks already tracked in CLAUDE.org
Still the right priorities: more portrait coverage (people with Cloudinary-only assets), expanding before/after beyond 4 people.
