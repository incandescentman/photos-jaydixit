** TODO Replace the homepage Packery masonry with a deterministic layout
- *Problem*: while loading, the homepage shows large blank regions; images pop into place one at a time as Packery re-lays-out; the grid overflows the viewport horizontally (horizontal scrollbar); even settled there's an empty region at bottom-right. The ~300-line custom "gap optimizer" (~src/pages/index.astro:90–381~) fights the layout engine.
- *Implementation options* (pick one):
  1. /Recommended:/ ~justified-layout~ (Flickr's algorithm — *already in package.json*). Compute row-based layout at build time in the frontmatter using the known aspect ratios from [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/data/image-metadata.json][📄 image-metadata.json]], emit absolutely-positioned items with inline ~top/left/width/height~. Zero client JS, zero CLS, no gaps by construction. PhotoSwipe still works unchanged.
  2. CSS Grid with ~grid-template-rows: masonry~ is still not cross-browser; skip.
  3. Plain CSS columns (like ~Gallery.astro~) — simplest, but loses left-to-right visual ordering.
- Once replaced, delete Packery, imagesloaded, draggabilly, and the gap-optimizer code. See also [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/docs/masonry-architecture-improvements.org][📄 masonry-architecture-improvements.org]] for earlier thinking on this.

** TODO Verify and document Supabase RLS on photo_user_likes
- *Problem*: [[file+emacs:/Users/jay/Dropbox/github/photos-jaydixit/src/components/PhotoLikeButton.astro][📄 PhotoLikeButton.astro]] inserts/deletes rows client-side keyed on a localStorage ~visitor_id~. No RLS policies are committed or documented anywhere in the repo. Unless RLS is locked down in the Supabase dashboard, anyone can forge or delete likes and manipulate /popular.
- *Implementation*:
  1. In the Supabase dashboard, confirm policies on ~photo_user_likes~: public ~SELECT~; ~INSERT~ allowed only with a ~unique(photo_id, visitor_id)~ constraint; ~DELETE~ restricted to rows matching the caller's own ~visitor_id~ (or disallowed entirely — accept that "unlike" only works via a soft client-side state).
  2. Commit the actual SQL (schema + policies) to a new ~supabase/schema.sql~ in the repo so it's documented and reproducible.
  3. Accept the residual risk: anonymous likes can never be fully tamper-proof without auth; the goal is raising the bar from "trivially scriptable" to "annoying."

** TODO Fix the unbounded /popular likes query
- *Problem*: ~src/pages/popular.astro:267~ fetches *every like row ever* (~select('photo_id')~) and counts client-side; it also renders a card for every photo on the site and hides zero-like ones in JS.
- *Implementation*: create a Postgres view or RPC in Supabase (~select photo_id, count(*) from photo_user_likes group by photo_id order by count desc limit 50~) and call that instead. Render only photos that have likes.
